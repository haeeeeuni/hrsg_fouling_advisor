관련 요구사항: FR-U-17, FR-U-18, FR-A-10 (모두 우선순위 P2)

> 이 문서의 기능은 핵심 기능(M1~M6) 완료 후 구현한다. 핵심 기능의 일정에 영향을 주지 않는다.

## 1. 자동 재계산 (FR-U-17)

### 1.1 목적
새 기간의 운전 데이터가 추가되었을 때, 이전에 사용한 설정으로 분석을 자동 재실행한다.

### 1.2 설정
```
AutoRecalcConfig
  - unit (OneToOne)
  - enabled : bool (기본 False)
  - trigger : 'ON_UPLOAD' | 'SCHEDULE'
  - schedule_cron : 문자열 (trigger=SCHEDULE 일 때, 예 '0 6 * * 1' 매주 월 06:00)
  - base_analysis_run (FK)      # 설정을 상속할 기준 분석
  - period_mode : 'ROLLING' | 'EXTEND'
      ROLLING : 최근 N개월 고정 창
      EXTEND  : 기준 분석 시작일 ~ 최신 데이터
  - rolling_months : 기본 12
  - retrain_model : bool (기본 False)
  - notify_on_grade_change : bool (기본 True)
  - updated_by / updated_at
```

### 1.3 동작
1. 트리거 발생(업로드 완료 또는 스케줄) → 신규 데이터 존재 여부 확인
2. `base_analysis_run`의 `settings_snapshot`과 `benefit_params_snapshot`을 그대로 적용
3. 기간을 `period_mode`에 따라 산정하고 분석 실행 (`AnalysisRun.is_auto = True`)
4. 완료 시 결과 비교: 이전 대비 FI 변화, 등급 변화, D-day 변화
5. 등급이 상승(정상→주의, 주의→경고)했으면 알림 생성

### 1.4 알림
- 앱 내 알림 센터(벨 아이콘) + 대시보드 배너. 이메일은 선택(사내 SMTP 설정 시).
- 알림 내용: 호기, 이전/현재 등급, 현재 FI, D-day, 분석 링크.

### 1.5 주의
- 자동 실행은 수동 실행과 동일한 이력으로 남되 `is_auto=True`로 구분한다.
- 동일 호기에 분석이 진행 중이면 건너뛰고 사유를 기록한다.
- 모델 자동 재학습은 기본 비활성(오염 구간으로 학습하면 기준이 오염되므로). 활성화 시 반드시 청정 기준 기간만 사용한다.

### 1.6 수용 기준
- [ ] AC-19-1: 자동 재계산이 켜진 호기에 데이터를 업로드하면 분석이 자동 실행되고 `is_auto=True`로 기록된다.
- [ ] AC-19-2: 등급이 주의→경고로 바뀌면 알림이 생성된다.
- [ ] AC-19-3: 자동 실행은 기준 분석의 설정값을 그대로 사용한다.

## 2. 백테스트 (FR-U-18)

### 2.1 목적
과거 세정 시점을 정답으로 두고, “그 이전 데이터만으로 예측했다면 얼마나 맞았는가”를 검증해 모델 신뢰도를 정량화한다.

### 2.2 절차
```
대상: 호기의 세정 이벤트 목록 (최소 2회 필요)

각 세정 이벤트 E(실제 일자 D_E)에 대해:
  1. 컷오프 날짜 C = D_E − lookahead_days (기본 60, 30/60/90 다중 평가)
  2. C 이전 데이터만 사용해 파이프라인 전체를 재실행
     (모델은 C 이전의 청정 기준 기간으로만 학습 — 미래 정보 누설 금지)
  3. 그 시점의 FI, 추세, 예측 D-day 산출 → 예측 도달일 P_E
  4. 오차 = P_E − D_E (일)
  5. 실제 세정 시점의 FI(사후 계산값)도 기록
전체 집계: 평균 절대 오차(MAE, 일), 편향(평균 부호), 적중률(±30일 이내 비율)
```

### 2.3 편익 검증
- 예측 편익 vs 실제 회복 기반 편익(세정 전후 비교 결과)을 비교해 편익 모델의 과대/과소 경향을 파악한다.
- 손실 계수(`dp_power_loss_coeff` 등) 보정 제안값을 제시한다(적용은 관리자 판단).

### 2.4 결과 표시
| 세정 이벤트 | 실제 일자 | 컷오프 | 예측 도달일 | 오차(일) | 그때의 FI | 실제 세정 시 FI |
|-------------|-----------|--------|-------------|----------|-----------|-----------------|
| 1차 | 2023-06-14 | 2023-04-15 | 2023-07-02 | +18 | 48.2 | 63.1 |
| 2차 | 2024-02-20 | 2023-12-22 | 2024-02-04 | −16 | 51.0 | 60.8 |

- 요약: `평균 절대 오차 17일 / 편향 +1일 / ±30일 적중률 100%`
- 산점도(예측 도달일 vs 실제 일자, 45° 기준선)

### 2.5 데이터 모델
`14-data-model.md`의 `BacktestResult` 참조.

### 2.6 주의
- **미래 정보 누설 금지**가 가장 중요하다. 컷오프 이후의 데이터·세정 이력·모델을 어떤 경로로도 사용하지 않는다.
- 세정 이벤트가 1회뿐이면 백테스트를 제공하지 않는다.

### 2.7 수용 기준
- [ ] AC-19-4: 백테스트 실행 시 컷오프 이후 데이터가 모델 학습·추세 적합에 포함되지 않는다.
- [ ] AC-19-5: 세정 이벤트별 예측 오차와 전체 MAE가 표로 표시된다.
- [ ] AC-19-6: 세정 이력이 1회 이하인 호기는 백테스트 메뉴가 비활성화된다.

## 3. 호기 간 오염도 비교 및 세정 우선순위 (FR-A-10)

### 3.1 목적
여러 호기를 동시에 운영할 때, 한정된 정비 자원을 어느 호기에 먼저 투입할지 판단한다.

### 3.2 비교 원칙
- 각 호기의 **최신 성공 분석 결과**를 사용한다. 분석 기준일이 크게 다르면 경고를 표시한다.
- 절대 차압·스택온도는 설비마다 달라 비교 불가하므로, **FI와 잔차 기반 지표만 비교**한다.
- 공통 군집(예: `L3-SU`)이 존재하는 경우 군집별 비교도 제공한다.

### 3.3 우선순위 점수
```
priority_score = w1·norm(FI)
               + w2·norm(진행 속도 slope_per_day)
               + w3·norm(일일 손실 비용)
               + w4·norm(1 / max(D-day, 1))

기본 가중치: w1=0.3, w2=0.2, w3=0.35, w4=0.15   (관리자 설정)
norm() : 비교 대상 호기들 사이의 min-max 정규화
```
- 점수가 높을수록 우선순위가 높다.
- 점수만으로 단정하지 않고, 근거 지표를 함께 표로 제시한다.

### 3.4 표시
| 순위 | 호기 | FI | 등급 | 진행속도(FI/일) | D-day | 일일 손실(원) | 예상 순편익(원) | 점수 |
|------|------|-----|------|-----------------|-------|----------------|------------------|------|
| 1 | 2호기 | 71.2 | 경고 | 0.22 | 이미 도달 | 6,930,000 | 8.9억 | 0.92 |
| 2 | 1호기 | 62.4 | 경고 | 0.18 | 이미 도달 | 5,712,000 | 7.7억 | 0.81 |
| 3 | 3호기 | 34.8 | 주의 | 0.09 | D-278 | 1,840,000 | 2.1억 | 0.31 |

- 호기별 FI 시계열 오버레이 차트
- 각 호기의 분석 기준일·신뢰도를 함께 표기

### 3.5 수용 기준
- [ ] AC-19-7: 3개 호기의 최신 분석 결과로 우선순위 표가 생성된다.
- [ ] AC-19-8: 분석이 없는 호기는 목록에서 “분석 필요”로 표시된다.
- [ ] AC-19-9: 우선순위 가중치를 변경하면 순위가 즉시 재계산된다.

## 4. 구현 메모 (2026-09-21, Phase 7)

명세에 없던 결정과 해석을 남긴다(AGENTS.md §9.7).

### 4.1 컷오프가 닿아야 하는 지점 (§2.6 구체화)
"어떤 경로로도 사용하지 않는다"가 실제로 의미하는 곳은 `analysis/pipeline.py` 의 네 지점이다.
`PipelineContext.cutoff` 하나가 전부를 관통한다.

| # | 지점 | 막는 누설 |
|---|------|-----------|
| 1 | `load_measurements` 의 조회 상한 | 컷오프 이후 계측값이 정제·학습·FI 에 들어감 |
| 2 | `resolve_baseline` 의 관리자 지정 기간 필터 | 아직 등록되지 않았을 청정 기준 기간을 씀 |
| 3 | `resolve_baseline` 의 세정 이력 필터 | 미래 세정을 기준으로 청정 구간을 잡음 |
| 4 | `_last_cleaning_naive` 의 세정 이력 필터 | 미래 세정으로 추세 구간을 절단함 |

추가로 컷오프 실행은 `ClusterDefinition` 과 `ModelVersion` 을 **저장하지 않는다**.
과거 시점 재현이 운영 중인 군집 정의·활성 모델을 덮으면 안 되기 때문이다.
백테스트용 `AnalysisRun` 도 트랜잭션을 롤백해 운영 이력과 섞이지 않게 한다.

**한 곳만 빠뜨려도 예외 없이 그럴듯한 숫자가 나오므로** 전용 누설 테스트
(`analysis/tests/test_backtest_no_leakage.py`)로 지점마다 고정한다. 그 중
`test_cutoff_result_differs_from_full_run` 은 컷오프 인자가 조용히 무시되는 경우를 잡는다.

### 4.2 §2.4 "실제 세정 시 FI" 의 출처
컷오프 실행에서는 정의상 알 수 없는 값이다. **컷오프 없이 돌린 최신 성공 분석**의 FI 시계열에서
해당 날짜 값을 읽어 참고로 붙인다(사후 계산값이며 예측에는 쓰지 않는다).
전체 기간 분석 결과가 없으면 `NO_FULL_RUN` 경고를 남기고 빈 값으로 둔다.

### 4.3 §2.3 계수 보정 제안의 산식
"실제 회복 기반 편익"을 직접 원(₩)으로 재구성하는 대신, 손실 모델에서 **편익이 Δ차압에 비례**한다는
성질을 이용한다.

```
예측값 = 세정 직전 성공 분석의 BenefitResult.delta_dp_kpa
실적값 = 그 세정의 ComparisonReport metrics 중 residual_dp 의 delta 를 부호 반전한 회복량
보정 배수 = median(실적값 / 예측값)
```

- 세정 후 오히려 악화된 사례(실적값 음수)도 **제외하지 않는다.** 빼면 보정이 낙관 쪽으로 쏠린다.
- 다만 음수 배수는 계수로 쓸 수 없으므로 0 에서 끊는다.
- 세정 전후 비교 결과가 없는 세정은 짝을 만들지 않으며, 짝이 하나도 없으면 제안을 내지 않는다.

### 4.4 다중 컷오프 지점
`lookahead_days` 를 지정하지 않으면 설정 `backtest_lookahead_days`(기본 `[30, 60, 90]`)의
모든 지점을 평가하고 **지점마다 `BacktestResult` 1건**을 남긴다. 화면에서 지점을 골라 비교한다.
±30일 적중 판정 폭은 `backtest_hit_window_days` 설정이다(코드 상수 아님).

### 4.5 §1.3 ROLLING 기간의 해석
`ROLLING` 은 기준 분석의 시작일에 얽매이지 않고 **최신 데이터 기준으로 창을 민다**.
기준 분석 시작일을 하한으로 두면 창이 계속 넓어져 `EXTEND` 와 구분되지 않기 때문이다.

### 4.6 §3.2 "분석 기준일이 크게 다르면 경고" 의 기준
호기 간 최신 분석 일시의 최대 격차가 **30일**을 넘으면 화면에 경고를 띄운다.
같은 시점 기준으로 다시 분석한 뒤 비교하도록 안내한다.

### 4.7 API 엔드포인트
`15-api.md` §12 참조. 자동 재계산 설정은 `GET`/`PUT` 으로 나눴고, 백테스트 가용성 조회
(`/backtests/availability/`, AC-19-6)와 알림 읽음 처리 엔드포인트를 추가했다.
