# 01. 인증과 사용자

관련 요구사항: AUTH-1 ~ AUTH-12

---

## 1. 목적

승인된 사람만 앱을 쓰게 한다. 외부인도 소개 화면과 회원가입 화면에는 접근할 수 있으므로,
**가입만으로는 아무 기능도 쓸 수 없고 관리자가 승인해야 로그인할 수 있다.**

> 기술 프롬프트는 "사용자는 로그인 없이 채팅"을 요구했지만, 이 앱은 회원가입 + 승인으로 대체한다(결정 2026-10-10).
> 내부 자료 기반 답변과 계산 결과가 외부에 무단으로 노출되는 것을 막기 위해서다.

## 2. 사용자 모델

Django `AbstractUser` 를 상속한다. **사용자와 관리자는 같은 모델이고 `role` 로 구분한다.**

| 필드 | 타입 | 설명 |
|---|---|---|
| `username` | 문자열, unique | **로그인 ID.** `USERNAME_FIELD`(AbstractUser 기본). 소문자로 정규화해 저장 |
| `password` | 해시 | Django 기본 해셔 |
| `full_name` | 문자열(50) | 성명. 필수 |
| `organization` | 문자열(100) | 소속(회사·부서). 필수 |
| `email` | 이메일 | 선택. 연락용이며 앱이 메일을 보내지는 않는다 |
| `signup_reason` | 텍스트(500) | 가입 사유. 선택 |
| `role` | `USER` \| `ADMIN` | 기본 `USER` |
| `approval_status` | `PENDING` \| `APPROVED` \| `REJECTED` | 기본 `PENDING` |
| `approved_by` · `approved_at` | FK · 일시 | 승인·반려 처리자와 시각 |
| `rejection_reason` | 텍스트(500) | 반려 사유 |
| `is_active` | bool | 비활성화(가입 승인과 별개). 비활성이면 로그인 불가 |
| `must_change_password` | bool | 기본 관리자·비밀번호 초기화 직후 `True` |

- `first_name`, `last_name` 은 쓰지 않는다(`full_name` 하나로).
- **앱 권한은 `role == 'ADMIN'` 으로만 판정한다.** `is_staff`/`is_superuser` 는 Django `/admin/` 접근용이다.
- ID 규칙: 영문 소문자·숫자·`.`·`_`·`-`, 4~30자. 대소문자 구분 없이 중복 불가(저장 전 소문자 변환).

> **마이그레이션 주의.** 기존 코드는 `username` 을 제거하고 `employee_no` 를 `USERNAME_FIELD` 로 썼다.
> 커스텀 User 의 `USERNAME_FIELD` 는 첫 마이그레이션 이전에 확정해야 하므로, 전환 시 `accounts` 마이그레이션을
> 새로 시작한다. 데모 DB 의 기존 계정은 보존하지 않는다(`changes-2026-10.md` §3).

## 3. 회원가입 (AUTH-1 ~ AUTH-3)

- **AUTH-1** 비로그인 사용자는 `/signup` 에서 ID, 비밀번호, 비밀번호 확인, 성명, 소속, 이메일(선택), 가입 사유(선택)를 입력해 가입을 신청한다.
- **AUTH-2** 신청 직후 상태는 `PENDING` 이다. 화면에 "관리자 승인 후 로그인할 수 있습니다"를 보여 준다. **자동 로그인하지 않는다.**
- **AUTH-3** ID 중복이면 "이미 사용 중인 ID 입니다"를 보여 준다(가입 화면에서는 ID 존재 여부 노출을 허용한다 — 중복 안내 없이는 가입할 수 없다).
- 가입 API 는 IP 기준 시간당 10회로 제한한다(스팸 가입 방지). E2E 처럼 한 IP 에서 가입을 반복하는 환경만
  환경 변수 `THROTTLE_SIGNUP`(예: `1000/hour`)으로 올린다.

## 4. 승인 (AUTH-4, AUTH-5)

- **AUTH-4** 관리자는 승인 대기 목록에서 신청자 정보를 보고 **승인** 또는 **반려(사유 필수)** 한다.
  처리 결과는 감사 로그에 남는다.
- **AUTH-5** 반려된 사용자는 같은 ID 로 다시 가입할 수 없다. 관리자가 반려된 신청을 **승인**하거나 계정을 삭제하면 다시 쓸 수 있다
  (반려 → 승인 대기로 되돌리는 별도 동작은 두지 않는다 — 다시 검토할 일이면 바로 승인하면 된다).
- 관리자 화면 상단에 승인 대기 건수 배지를 표시한다. 이메일·외부 알림은 보내지 않는다.

## 5. 로그인 (AUTH-6 ~ AUTH-8)

- **AUTH-6** 로그인은 **ID + 비밀번호** 두 요소다. 화면 **상단 우측**의 로그인 버튼에서 연다(`11-frontend.md` §3).
- 인증 절차:
  1. `username`(소문자 변환)으로 조회. 없으면 실패
  2. 비밀번호 검증. 틀리면 실패
  3. `approval_status` 확인 — `PENDING` 이면 "관리자 승인 대기 중입니다", `REJECTED` 면 "가입이 반려되었습니다(사유: …)"
  4. `is_active == False` 면 "비활성화된 계정입니다. 관리자에게 문의하세요"
  5. 성공 — 세션 발급, 로그인 이력 기록
- **AUTH-7** 1·2단계 실패 문구는 **"ID 또는 비밀번호가 올바르지 않습니다"** 로 통일한다.
  3·4단계 안내는 비밀번호가 맞았을 때만 보여 주므로 계정 존재 여부가 노출되지 않는다.
- **AUTH-8** 같은 ID 로 5회 연속 실패하면 5분간 잠근다(횟수·시간은 설정 `login_max_failures`·`login_lockout_minutes`).
  **ID·비밀번호가 틀린 시도만 센다** — 승인 대기·반려·비활성 안내는 비밀번호가 맞았다는 뜻이라 세지 않는다.
  IP 기준 분당 10회 스로틀도 유지한다.
- 세션: 세션 쿠키(HttpOnly, SameSite=Lax) + CSRF. 8시간 무활동 시 만료. JWT 는 쓰지 않는다.

## 6. 기본 관리자 (AUTH-9)

- **AUTH-9** 앱 시작 시 **활성 관리자(`role=ADMIN`, `APPROVED`, `is_active`)가 한 명도 없으면** 다음 계정을 만든다.

  | ID | 비밀번호 | 성명 | 소속 |
  |---|---|---|---|
  | `admin` | `admin1234!` | 관리자 | 시스템 |

  - 상태는 `APPROVED`, `must_change_password=True`. 첫 로그인 후 비밀번호 변경 배너를 표시한다.
  - "앱 시작 시"는 컨테이너 시작 명령(`migrate` → `seed_defaults` → 서버 기동)에서 실행하는 것을 뜻한다.
    `AppConfig.ready()` 에서 DB 를 쓰지 않는다(마이그레이션 전에도 호출되기 때문).
  - 멱등이다. 다른 활성 관리자가 있으면 `admin` 을 지웠어도 다시 만들지 않는다(삭제한 기본 계정이 되살아나는 보안 구멍 방지).
  - TODO(질문): 기술 프롬프트의 "기본 관리자 계정이 없을 경우"를 "활성 관리자가 없을 경우"로 해석했다.

## 7. 사용자 관리 (AUTH-10, AUTH-11)

- **AUTH-10** 관리자는 사용자 목록(ID·성명·소속·역할·승인 상태·활성·최근 로그인)을 검색·필터하고,
  성명·소속·이메일·역할·활성 여부를 수정하고, 비밀번호를 초기화한다(초기화 시 `must_change_password=True`).
- **AUTH-11** 마지막 활성 관리자는 비활성화·역할 변경·삭제할 수 없다. 자기 자신의 역할을 `USER` 로 낮출 수 없다.
- 삭제는 기본 비활성화. 물리 삭제는 대화·요청 건이 없는 계정만 허용한다.

## 8. 비밀번호 (AUTH-12)

- **AUTH-12** 최소 8자, 숫자만으로 된 비밀번호 금지(`MinimumLengthValidator(8)`, `NumericPasswordValidator`).
  기본 관리자 `admin1234!` 는 이 규칙을 만족한다.
- 본인 변경: 현재 비밀번호 확인 후 변경. 변경하면 `must_change_password=False`.
- 비밀번호는 로그·감사 로그 스냅샷에 남기지 않는다.

## 9. 접근 제어

| 경로 | 비로그인 | USER | ADMIN |
|---|---|---|---|
| 소개 `/`, 로그인, 회원가입 | ✔ | ✔ | ✔ |
| 홈, 질의응답, 계산기, 체크리스트, 내 정보 | – | ✔ | ✔ |
| 관리자 모드 `/admin/*` | – | – | ✔ |

- API 기본 권한은 `IsApprovedUser`(로그인 + `APPROVED` + 활성). 관리자 API 는 `IsAdminRole` 을 **명시**한다.
- 비인증 401, 권한 부족 403.

## 10. 수용 기준 (AC)

- [ ] AC-01-1 가입 신청 후 승인 전에는 올바른 비밀번호로도 로그인되지 않고 "승인 대기" 안내가 뜬다.
- [ ] AC-01-2 틀린 비밀번호로는 승인 대기 계정이라도 "ID 또는 비밀번호가 올바르지 않습니다"만 보인다.
- [ ] AC-01-3 관리자가 승인하면 즉시 로그인할 수 있고, 반려하면 사유가 로그인 시 보인다.
- [ ] AC-01-4 빈 DB 에서 시작하면 `admin` / `admin1234!` 로 로그인되고 비밀번호 변경 배너가 뜬다.
- [ ] AC-01-5 다른 활성 관리자가 있으면 `admin` 을 삭제한 뒤 재시작해도 `admin` 이 생기지 않는다. `seed_defaults` 를 두 번 실행해도 계정이 하나다.
- [ ] AC-01-6 `Admin`, `ADMIN` 처럼 대소문자만 다른 ID 로는 가입할 수 없다.
- [ ] AC-01-7 마지막 활성 관리자는 비활성화·강등·삭제할 수 없다.
- [ ] AC-01-8 승인 대기 사용자의 세션으로 어떤 업무 API 를 불러도 401/403 이다.
- [ ] AC-01-9 5회 연속 실패 후 5분간 해당 ID 로그인이 차단된다.
